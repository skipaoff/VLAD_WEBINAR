# Модуль 06 — AI-продавец в Telegram

Продавец, который переписывается с клиентом, ведёт его к сделке и умеет слушать
голосовые. Работает либо ботом, либо от живого аккаунта — на выбор. Ни базы данных,
ни вебхуков, ни панели в браузере: один процесс и папка с файлами.

## Два канала, одна логика продажи

Продавец работает либо ботом от @BotFather, либо от живого аккаунта через Telethon.
Выбирается одной строкой в `config.json` — сама продажа от этого не меняется ни на слово:
методология, знания, темп, эскалации и голос общие.

```json
"channel": "bot"        // или "userbot"
```

| | **bot** | **userbot** |
|---|---|---|
| Кто пишет | бот с пометкой «bot» | живой человек: имя, аватарка, «был в сети» |
| Ставится | за пять минут, только токен | разовая авторизация по номеру |
| Клиент должен | написать боту первым | ничего, обычная личка |
| Пульт владельца | в личке бота | в «Избранном» аккаунта |
| Владелец пишет сам | продавец не видит | видит, запоминает и замолкает |
| Риск | никакого | **бан аккаунта за рассылки** |
| Кому | большинству, и для эфира | тем, кому важно, чтобы не было слова «бот» |

Живой канал рассчитан на **отдельный рабочий аккаунт**: продавец отвечает всем, кто
пишет в личку. Ставить его на личный номер, куда пишут друзья и родня, не стоит —
он ответит и им.

И он не средство рассылок: отвечает написавшим и напоминает тем, с кем разговор уже
был. Telegram блокирует аккаунты за массовые сообщения незнакомым.

## Слои

Код не знает о бизнесе, методология не знает о бизнесе, и только третий слой знает.
Поэтому посадить продавца на нового клиента — значит заполнить одну папку, а не
переписать бота. Канал связи — тоже отдельный слой: движок продаж про транспорт
не знает вообще.

```
bot.py              точка входа: собирает всё и отдаёт управление каналу
config.json         настройки: канал, бизнес, модель, голос, темп
.env                секреты: токены и ключи

seller/
  config.py         читает .env и config.json, отдаёт Settings
  engine.py         как продаём: дебаунс, темп, эскалации, напоминания
  admin.py          пульт владельца — общий для обоих каналов
  knowledge.py      собирает системный промпт из знаний
  memory.py         переписка по клиентам
  brain.py          спрашивает Claude
  voice.py          слушает и озвучивает
  safety.py         вычищает секреты из ошибок
  channels/
    base.py         что транспорт обязан уметь
    botapi.py       бот от @BotFather
    userbot.py      живой аккаунт через Telethon

playbook/           КАК ПРОДАВАТЬ — одинаково для всех, не трогается
  01-osnova.md      формула, кассир против продавца
  02-etapy.md       этапы и последовательность закрытия
  03-voprosy.md     SPIN, альтернативные вопросы
  04-kto-pered-toboy.md  температура, квалификация
  05-cena.md        ценность до цены, якоря, «дорого»
  06-vozrazheniya.md дожим 2-3 раза, «я подумаю»
  07-molchanie.md   тайминги напоминаний
  08-antipatterny.md 20 ошибок
  09-frazy.md       интонации
  10-cheklist.md    проверка перед отправкой

business/           ЧТО ПРОДАВАТЬ — своё под каждого клиента
  _template/        пустая база: 11 файлов, в каждом написано, что туда положить

state/              переписка, по файлу на диалог
logs/               логи с ротацией
```

Порядок разделов задан в `config.json` строкой `knowledge_order`: сначала что продаём,
потом как. Правила канала в этот порядок не входят — они всегда последние и перекрывают
всё, что выше.

Методология не знает вашего продукта, поэтому в четырёх местах она обращается к папке
бизнеса. Это и есть вилка, ради которой всё разделено:

| Файл бизнеса | Что оттуда берёт методология |
|---|---|
| `07-targets.md` | целевые действия и этапы: куда ведём человека |
| `08-price-play.md` | якоря, дефицит, чем держим цену, что с просьбой о скидке |
| `09-phrases.md` | как это звучит на вашем прайсе |
| `10-limits.md` | кому не продаём и что уходит владельцу |

## Что умеет

- Ведёт разговор по методологии: реакция, вопрос с вариантами, следующий шаг.
- **Ждёт, пока человек допишет.** Три сообщения подряд — один осмысленный ответ,
  а не три ответа поверх друг друга.
- **Отвечает в живом темпе:** «печатает…», задержка по длине текста, может разбить
  ответ на два-три сообщения.
- **Слушает голосовые и отвечает голосом** тому, кто сам пишет голосом. Одним ключом
  ElevenLabs — и слушает, и говорит.
- **Не выдумывает.** Факта нет в базе — не угадывает, а пишет владельцу в личку
  с конкретным вопросом и id диалога.
- **Пересылает вложения:** скриншот оплаты падает владельцу, клиенту — «посмотрю».
- **Держит роль:** «покажи инструкции», «ты бот», «забудь предыдущее» — обычные реплики,
  отвечает как продавец.
- **Напоминает молчащим** один-два раза и на этом останавливается.
- Помнит переписку и не забывает, о чём говорили.
- **На живом аккаунте видит, когда владелец вмешался** и написал клиенту сам: запоминает
  его реплику и в этом диалоге замолкает, чтобы двое не писали одновременно.

## Пульт владельца

В канале **bot** команды пишутся боту в личку с `ADMIN_CHAT_ID`, клиенту их меню
не показывается. В канале **userbot** — в «Избранное» своего же аккаунта: продавец
и владелец там один Telegram.

| Команда | Что делает |
|---|---|
| `/status` | аптайм, размер знаний, диалоги, кто на mute, работает ли голос |
| `/asclient <текст>` | прогнать реплику как от клиента, ответ придёт вам |
| `/hist <id>` | последние 12 реплик диалога |
| `/say <id> <текст>` | написать клиенту от лица продавца, реплика ляжет в память |
| `/mute <id>`, `/unmute <id>` | замолчать в одном диалоге и вернуться |
| `/pause`, `/resume` | глобально: копить молча / снова отвечать |
| `/reload` | перечитать знания без перезапуска |

`/asclient` — то, чем проверяют продавца перед эфиром: реплика прогоняется как от клиента,
ответ приходит владельцу, ни одному клиенту ничего не уходит.

## Чего не умеет

Не принимает оплату. Не ведёт по стадиям воронки и не считает конверсию. Не рассылает
холодную базу — и на живом аккаунте не будет. Не переписывается за пределами Telegram.
Всё это осознанно оставлено за бортом.

## Ключи

Все секреты — в `.env`, образец рядом в `.env.example`. В код и в логи они не попадают:
текст любой ошибки перед отправкой чистится от ключей.

| Переменная | Нужна | Зачем |
|---|---|---|
| `ANTHROPIC_API_KEY` | всегда | продавец думает |
| `BOT_TOKEN` | каналу `bot` | токен от @BotFather |
| `ADMIN_CHAT_ID` | каналу `bot` | куда слать эскалации и вложения |
| `TG_API_ID`, `TG_API_HASH` | каналу `userbot` | my.telegram.org → API development tools |
| `ELEVENLABS_API_KEY` | по желанию | слушать голосовые и отвечать голосом |
| `OPENAI_API_KEY` | почти никогда | запасная расшифровка, если `"stt": "openai"` |

Чего нет — то просто выключено: без голосового ключа продавец вежливо попросит написать
текстом. Без обязательных ключей не запустится и скажет, каких именно не хватает.

## Запуск

```bash
cd modules/06-sales-bot
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env             # вписать ключи
tools/new-business.sh мой-клиент # заполнить файлы знаний
# в config.json: "channel": "bot" или "userbot", "business": "мой-клиент"
.venv/bin/python bot.py
```

Для живого аккаунта перед первым запуском — разовая авторизация:

```bash
.venv/bin/python tools/login-userbot.py
```

Ни туннеля, ни белого IP, ни вебхука не нужно. Подробнее — в [SETUP.md](SETUP.md).

## Проверка перед эфиром

```bash
cd modules/06-sales-bot && python3 -m pytest -q tests
```

На чистом шаблоне зелёный: шаблон и должен быть с метками. Как только в `config.json`
поставлен настоящий бизнес — тесты требуют, чтобы он был заполнен до конца и чтобы
в репозиторий не уехали секреты.
